## 3. Account lifecycle and transition requirements

### 3.1 State model and cross-transition controls

The following are **conceptual lifecycle stages**, not chosen enum names, database fields or a rigid mandated order: request under review; created but not eligible for access; credential initialization/activation pending; active; suspended/deactivated; authorized reinstatement; archival/removal. Password recovery and credential changes are guarded operations, not necessarily separate persistent account states. Credential completion does not alone authorize activation; activation does not waive an approved MFA requirement.

Recommended traceable controls:

- **ID-01:** stable backend identity independent of editable username/display values; approved login normalization/uniqueness/reuse and owner verification. No browser `akun`, seed or client-supplied privileged identifier establishes identity.
- **ID-02:** deny unauthorized/unknown lifecycle action, target or writable field; explicit administrative approval, minimal grants, account status and relevant assurance verified on the server for every request.
- **ID-03:** identity/status/credential/permission updates use consistent transaction/version rules and attributable audit. No success response for an uncommitted privileged change; approved handling of unavailable audit/store must avoid unaudited success or partial privilege assignment.
- **ID-04:** suspension/deactivation blocks issuance and subsequent authorized operations immediately at the server authorization boundary; old credentials, sessions, remember-device artifacts and recovery/activation capabilities must not reactivate access. A durable account/session validity or revocation check must work across instances, not just delete one browser cookie. Recheck before committing security-sensitive operations so concurrent/in-flight changes cannot bypass revocation; specify long-running operation/notification behavior before implementation. No arbitrary grace period is approved.
- **ID-05:** lifecycle records preserve approved audit/provenance and minimize personal data; archive/removal and credential/session destruction follow an approved retention/recovery process, not automatic cascade deletion or an invented legal requirement.

### 3.3 Recovery and revocation invariants

Credential recovery is not permission management. An administrator initiating a recovery flow need not see or choose the user's password. Recovery must not reinstate an inactive account, grant privileges or silently remove factors. Last-administrator loss is an approved bootstrap/recovery runbook, not public registration. Current browser logout affects local state only (SRC7); it is not evidence of L6-L10 revocation.

Session/credential/grant changes must be attributable and testable under concurrent requests. Deleting stored sessions alone is insufficient if other replicas, remember-me mechanisms, cached grants or in-flight privileged requests can recreate/retain authority. Select a consistent backend validity strategy after persistence/session approvals, without mandating schema here. Already delivered/downloaded data cannot be remotely erased by revocation; residual impact and incident handling need review.

## 4. Initial administrator bootstrap analysis

| Approach / hazard | Security and operational assessment |
|---|---|
| Public registration / first signup gets administrator | Unauthorized ownership and takeover race; conflicts with confirmed enrollment. Not recommended; no signup route introduced. |
| Hardcoded/default/shared administrator password/account | Known/reused secrets, poor attribution and copying into logs/source; shared ownership prevents trustworthy audit. Not recommended; no sample credential supplied. |
| Unauthenticated setup route / secret URL alone | Discovery, replay, network exposure and accidental re-enable; obscurity is not authorization. Not recommended. |
| Reviewed out-of-band operator bootstrap | **Recommended candidate:** explicitly authorized operator using approved restricted environment/channel provisions a verified named person through the same validation/minimal-grant/audit rules; secure initialization instead of known password. Transport (operator command/runbook/etc.) remains unselected. |

**BOOT-01 prerequisite:** organization identifies initial approving authority, performer, verified recipient and approved evidence, custody and minimal initial capability. No job title or approval chain is inferred. Bootstrap cannot depend circularly on an existing app administrator, but the out-of-band operator must still be authorized and attributable.

**BOOT-02 proposed safety:** only approved initialization conditions, explicit target/environment, no grants from arbitrary flags/browser role fields; record execution/approval, prevent duplicate/replayed bootstrap and atomically protect against simultaneous first-account attempts. Subsequent invocation should safely refuse/no-op under the reviewed rule, never overwrite credentials or create a second unrestricted administrator silently. Do not assume an empty table alone proves bootstrap authorization.

**BOOT-03 recovery:** define a separately approved lost-last-administrator or compromised-bootstrap process with verified custodian access, minimal temporary scope, review/audit and removal of temporary authority. Any emergency/duty exception must be explicitly authorized; no permanently privileged hidden account. Tests B01/B02 below are planned only. No bootstrap logic, operator command, credentials or seed is implemented.

## 6. Sanctum, origins, CORS, CSRF and cookies

The following are **conditional proposed requirements**, not installed settings. Sanctum SPA uses Laravel session authentication, not a browser bearer-token requirement. Sibling domains are different origins; same-site does not eliminate CORS or CSRF.

| ID | Requirement and needed decision |
|---|---|
| SPA-01 | Approve actual frontend/API domain topology per environment, first-party compatibility/stateful domains including ports, trusted host/proxy mapping and HTTPS for operational credentials. Laravel Cloud planned does not prove DNS/TLS/resource configuration. Validate controlled staging parity before production. |
| SPA-02 | Use exact approved credentialed CORS origin allowlist, methods/headers/preflight; never wildcard or reflect arbitrary origins with credentials. CORS controls browser readability, not all request execution or authorization; protect state-changing requests separately. No blind cross-site cookie workaround. |
| SPA-03 | Approve session cookie Secure/HttpOnly, minimum safe domain/path scope and SameSite compatible with topology. CSRF cookie is intentionally readable; do not make it HttpOnly then bypass CSRF to compensate. Do not broaden parent cookie scope without reviewing every trusted sibling. SameSite alone is not full CSRF protection. |
| SPA-04 | Initialize CSRF context through the selected framework-convention mechanism; send valid CSRF header/token on required unsafe requests including login/logout; validate session association and reject mismatches. Framework's conventional CSRF-cookie route is a future package behavior, not existing PINTU functionality. Avoid business mutation through GET. |
| SPA-05 | Cross-origin React requests include credentials and correct decoded CSRF header; safe 401/403/419 handling without replaying unsafe actions automatically. Backend auth endpoints/contracts and adapter modifications need separate authorization. Current fetch and static prototype login do not satisfy this. |
| SPA-06 | Separate dev/staging/production origins, secrets, session/cache stores and database targets. Local hostname/port consistency and scoped approved dev TLS exceptions must not leak to production; debug disabled, public artifact boundary retained, no secret `VITE_*`. |

Approve cookie scope, TLS/proxy handling, SameSite, origins and CSRF transport together (P9). Session and CSRF cookies require correct separate treatment. Credentials may be delivered via intentional secure HTTP mechanisms, not ordinary JSON/logs. Current API health is unauthenticated and must not be claimed to test auth configuration. No topology or environment file is changed here.

## 8. Administrative access and permission boundaries

**ADM-01:** authenticate server identity/status/assurance, then authorize the precise action/target/field. Approve the following minimum capability/process matrix before exposing identity management; capabilities are categories, not named roles or assigned grants.

| Administrative surface | Minimum decision needed / boundary |
|---|---|
| Account provisioning | Who verifies/approves/performs creation, allowed targets and initial grants; no public registration or blanket administrator power |
| Activation/deactivation/reinstatement | Authorized status actor and reason/review, immediate revocation, concurrent changes and last-admin protection/recovery |
| Credential initialization/recovery | Who may initiate/verify/deliver, verified subject/custody and factor/status boundaries; not entitlement to view/change any secret arbitrarily |
| Permission assignment/revocation | Approved grantable scope, delegation, self-target restrictions and revocation consistency; assignment permission does not imply unlimited grants |

| Business approval/publication | Separate business governance and object-level matrix needed before business APIs. Identity administration is not content approval authority. |

**ADM-02:** propose least privilege and deny by default, controlled target scope, no unapproved self-grants/self-approval and independent review of high-impact changes. Actual separation-of-duty combinations/exceptions, who may approve and last-admin safeguards require business/security approval (P1/P7), not an invented two-person policy.

| Risk | Proposed control / open decision |
|---|---|
| Single unrestricted administrator | Minimize capability bundles, attributable named individuals, independent review/restore access; staffing constraints/exceptions documented by designated authority, not a shared all-powerful account |
| Self-assignment/own sensitive-change approval | Enforce approved grant ceilings/duties on server and log actor/target/approval; self-action permitted only under explicitly reviewed scope |

| Stale sessions after grant removal | SES-04 revalidation/invalidation at request/commit boundary; cached UI permissions never override current server policy |
| Recovery or bulk administration abuse | Separate recovery/status/grant authorities, scoped audit and atomic batches; no credential reset that silently grants/reactivates account; no production reset/import/clear-audit route inferred from prototype methods |

**ADM-03:** account/permission mutation and required authoritative audit commit together or meet an explicitly approved durable consistency design; no successful privileged mutation without attributable evidence. Audit identity established on server; failed/unknown login does not falsely attribute an actor merely from supplied username. Store only approved minimal attempted-subject metadata; failure reason detail can remain protected, not public enumeration. Retention, IP/device metadata and deletion/archival policy require approval (P8).

## 9. Practical threat model and verification mapping

Assets: credentials/recovery capabilities; authenticated sessions/assurance; identity status/grants; account/audit integrity; private employee/citizen data accessed after future integration; infrastructure secrets and public/private serving boundaries. Actors include unauthenticated remote attackers, malicious or compromised authenticated users, overprivileged/compromised operators and accidental configuration changes. Trust boundaries: browser/storage to backend, origin/cookie/CSRF to session, operator bootstrap/recovery to identity, backend to MySQL/shared sessions/audit and deployment/static output. No likelihood scores or legal classification invented.
